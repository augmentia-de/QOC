Hier ist das architektonische Konzept und wie du dieses dynamische Verhalten in Java umsetzt:
1. Das Kernprinzip: Der strukturierte Feedback-Loop nach jedem Schritt

Nach jedem ausgeführten Workflow-Schritt (Node) passiert folgendes:

    Zustandsaktualisierung: Das Ergebnis des Agenten oder Tools wird in den aktuellen Knoten des Baums geschrieben.

    Reflexions-Prompt: Der gesamte Baum (der ja gleichzeitig der Workflow-Plan und der Kontext ist) wird an das LLM übergeben.

    Strukturierte Entscheidung (Structured Output): Das LLM antwortet nicht mit Freitext, sondern mit einer strukturierten Anweisung (z. B. via JSON-Mode oder Function Calling), wie es weitergehen soll.

2. Die vier Steuerungs-Modi im isomorphen Modell

Das LLM entscheidet nach jedem Schritt anhand des Baum-Zustands über einen von vier Wegen:

    CONTINUE (Weiter): Alles läuft nach Plan. Der Zeiger (Pointer) springt zum nächsten definierten Knoten im Baum.

    ROLLBACK / GO_BACK (Zurück): Der aktuelle Schritt ist fehlgeschlagen oder hat unvorhergesehene Daten geliefert. Da dein System ein unveränderliches (immutable) Datenmodell (z. B. mit Java Records) nutzt, kannst du einfach auf einen früheren Snapshot des Baums zurückspringen und einen anderen Weg einschlagen.

    REPLAN (Neu planen): Das LLM stellt fest, dass die bisherigen Annahmen falsch waren. Es ersetzt den zukünftigen Teil des Workflow-Baums dynamisch durch einen neuen Teilbaum, den es selbst generiert.

    FINISH (Abschluss): Das Ziel ist erreicht.

Die Engine arbeitet rekursiv oder iterativ den Baum ab:

public class WorkflowEngine {

    public ExecutionResult executeStep(Node currentNode, WorkflowContext context) {
        // 1. Schritt ausführen (Agenten aufrufen)
        NodeResult result = agentExecutor.run(currentNode, context);
        
        // 2. Kontext & Workflow-Baum mit Ergebnis aktualisieren
        Node updatedNode = currentNode.withResult(result);
        
        // 3. LLM nach nächster Aktion fragen (übergibt den aktuellen Baum als JSON/Prompt)
        LLMDecision decision = llmPlanner.evaluateNextStep(updatedNode, context);
        
        // 4. Auf Basis der Entscheidung steuern
        return switch (decision.action()) {
            case CONTINUE -> advanceToNext(updatedNode);
            case GO_BACK -> rollbackTo(decision.targetNodeId());
            case REPLAN -> replaceSubtreeAndContinue(updatedNode, decision.replacementSubtree());
            case FINISH -> ExecutionResult.success(updatedNode);
        };
    }
}

3. Defense in Depth: Das Sicherheitsnetz in Java

Auch bei erzwungener Schema-Validierung kann es semantische Fehler geben (z. B. das LLM verweist auf eine targetNodeId, die im Baum gar nicht existiert). Deshalb fängst du das in Java wie folgt ab:

        Existiert die targetNodeId im aktuellen Baum?

        Sind alle Pflichtfelder der neuen Node-Teilbäume gefüllt?

        Ist der Graph zyklenfrei (keine Endlosschleifen im Re-Plan)?

    Automatischer Selbstheilungs-Loop (Self-Correction):
    Schlägt die semantische Validierung fehl (z. B. ID nicht gefunden), fängst du die Exception ab, packst die genaue Fehlermeldung (z. B. "Node mit ID 'step_99' existiert nicht") zusammen mit dem JSON in einen neuen Prompt und schickst das Ganze zurück an das LLM mit der Bitte um Korrektur. Das LLM korrigiert seinen Fehler im nächsten Versuch fast immer im Handumdrehen.

Hier ist ein sauberes Java-Beispiel für einen Self-Healing-Loop (Selbstheilungs-Schleife).

Das Prinzip ist einfach: Wenn das LLM einen ungültigen Baum generiert (entweder syntaktisch durch falsches JSON oder semantisch durch verbotene IDs), fängst du die Exception ab, reicherst den ursprünglichen Prompt mit der exakten Fehlermeldung an und schickst ihn zurück an das LLM. Das LLM verhält sich dadurch wie ein Programmierer, der einen Compiler-Fehler behebt.
Java-Code-Beispiel
Java

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class SelfHealingWorkflowPlanner {

    private static final Logger log = LoggerFactory.getLogger(SelfHealingWorkflowPlanner.class);
    private static final int MAX_RETRIES = 3;

    private final LLMClient llmClient; // Dein LLM-Client (z.B. LangChain4j, Spring AI oder direkt OpenAI API)
    private final ObjectMapper objectMapper;
    private final WorkflowValidator validator;

    public SelfHealingWorkflowPlanner(LLMClient llmClient, ObjectMapper objectMapper, WorkflowValidator validator) {
        this.llmClient = llmClient;
        this.objectMapper = objectMapper;
        this.validator = validator;
    }

    public LLMDecision planNextStepWithHealing(String currentWorkflowTreeJson) {
        String currentPrompt = "Analysiere den aktuellen Workflow-Baum und entscheide über den nächsten Schritt:\n" 
                + currentWorkflowTreeJson;

        for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
            try {
                log.info("Starte LLM-Planungsversuch {} von {}", attempt, MAX_RETRIES);

                // 1. LLM aufrufen
                String rawJsonResponse = llmClient.generate(currentPrompt);

                // 2. Syntaktische Validierung & Deserialisierung (Jackson)
                LLMDecision decision = objectMapper.readValue(rawJsonResponse, LLMDecision.class);

                // 3. Semantische Validierung (z. B. "Existiert die targetNodeId überhaupt?")
                ValidationResult validationResult = validator.validate(decision, currentWorkflowTreeJson);
                if (!validationResult.isValid()) {
                    throw new SemanticValidationException(validationResult.getErrorMessage());
                }

                log.info("Erfolgreiche und valide Entscheidung vom LLM erhalten.");
                return decision;

            } catch (JsonProcessingException e) {
                // Fall A: Das LLM hat kaputtes JSON geliefert
                log.warn("Syntaktischer JSON-Fehler im Versuch {}: {}", attempt, e.getMessage());
                currentPrompt = buildCorrectionPrompt(currentWorkflowTreeJson, 
                        "Dein letztes JSON war syntaktisch ungültig. Fehler: " + e.getMessage());

            } catch (SemanticValidationException e) {
                // Fall B: JSON ist valide, aber macht semantisch keinen Sinn (z. B. ungültige ID)
                log.warn("Semantischer Validierungsfehler im Versuch {}: {}", attempt, e.getMessage());
                currentPrompt = buildCorrectionPrompt(currentWorkflowTreeJson, 
                        "Deine Entscheidung enthält logische Fehler im Workflow-Baum: " + e.getMessage());
            }
        }

        throw new IllegalStateException("LLM konnte nach " + MAX_RETRIES + " Versuchen keinen validen Workflow-Baum generieren.");
    }

    private String buildCorrectionPrompt(String originalTreeJson, String errorMessage) {
        return String.format(
            "ACHTUNG: Dein vorheriger Versuch ist fehlgeschlagen!\n\n" +
            "Fehlerdetails:\n%s\n\n" +
            "Bitte korrigiere den Fehler. Hier ist nochmal der originale Workflow-Baum als Referenz:\n%s\n\n" +
            "Antworte AUSSCHLIESSLICH mit dem korrigierten JSON im exakten Schema.",
            errorMessage, originalTreeJson
        );
    }
}

Was in diesem Loop passiert:

    Versuch 1: Das LLM bekommt den aktuellen Baum. Bei komplexen Strukturen machen selbst gute LLMs hin und wieder kleine Fehler (z. B. sie vergessen ein Pflichtfeld im Record oder referenzieren eine Node-ID, die nicht existiert).

    Der Catch-Block:

        Schlägt das JSON-Parsen fehl, greift JsonProcessingException.

        Schlägt die fachliche Prüfung (z. B. ID-Check) fehl, wirft validator.validate() eine SemanticValidationException.

    Der Korrektur-Prompt: Statt den Prozess abzufbrechen, wird der Fehler wörtlich an das LLM zurückgespielt ("Dein vorheriger Versuch ist fehlgeschlagen! Fehlerdetails: Node 'step_xyz' nicht gefunden...").

    Ergebnis: In der Praxis korrigieren State-of-the-Art Modelle (wie GPT-4o oder Claude 3.5 Sonnet) ihren Fehler im 2. Versuch in über 95 % der Fälle vollautomatisch.

Wie soll die Ziel Definition je Schritt aussehen, format wird geprüft aber fachlich Validierung

Das ist eine der wichtigsten Fragen in autonomen Agenten-Architekturen! Die syntaktische Validierung (JSON-Schema, Typen) stellt nur sicher, dass die Datenstruktur stimmt. Die fachliche (semantische) Validierung muss hingegen prüfen, ob der Agent sein eigentliches Ziel in diesem Schritt auch inhaltlich korrekt erreicht hat.

Da dein System isomorph ist (Workflow und Kontext haben dieselbe Struktur), sollte die Ziel-Definition direkt als Metadaten-Objekt in jedem Knoten (Node) verankert sein.

Hier ist ein bewährtes Konzept, wie du die Ziel-Definition je Schritt aufbaust und fachlich validierst:
1. Wie sieht die Ziel-Definition im Knoten aus?

Jeder Workflow-Knoten sollte nicht nur die auszuführende Aufgabe (Prompt/Tool) enthalten, sondern auch explizite Erfolgskriterien (Success Criteria).

Im isomorphen Datenmodell sieht das als Java Record so aus:
Java

public record NodeGoal(
    String description,              // Sprachliche Beschreibung des Ziels (für das LLM)
    List<ValidationRule> rules,      // Programmatische Regeln (z. B. "Wert > 0", "Regex match")
    EvaluationStrategy strategy      // CODE_ONLY, LLM_JUDGE, oder HYBRID
) {}

public record ValidationRule(
    String fieldPath,   // Welches Feld im Ergebnis soll geprüft werden? (z.B. "output.score")
    RuleType type,      // GREATER_THAN, EQUALS, NOT_NULL, REGEX
    String expectedValue // Der erwartete Wert
) {}

Da dieser Baum dem LLM im Kontext übergeben wird, weiß das LLM bei jedem Schritt exakt, welches Ziel es erreichen muss und woran sein Erfolg gemessen wird.
2. Die drei Säulen der fachlichen Validierung

Für die eigentliche Prüfung nach einem Schritt hast du drei strategische Optionen, die du je nach Knotentyp einsetzen kannst:
A. Deterministische / Programmatische Validierung (Code-basiert)

Für harte geschäftliche Regeln (Business Logic), die keine KI brauchen:

    Beispiel: Der Schritt "Rechnung berechnen" liefert ein Ergebnis. Die Regel prüft: output.total >= 0 und output.currency == "EUR".

    Umsetzung: Ein einfacher Java-Validator, der die ValidationRules aus dem Knoten ausliest und gegen das JSON/Java-Objekt prüft.

B. LLM-as-a-Judge (Semantische Validierung)

Wenn das Ergebnis qualitativ ist (z. B. "Schreibe eine Zusammenfassung" oder "Prüfe, ob der Text keine Vorurteile enthält"):

    Ein kleiner, schneller LLM-Aufruf (oder derselbe Agent) bekommt:

        Das definierte Ziel des Knotens (NodeGoal.description).

        Den Output des Agenten.

    Die Aufgabe des Evaluators ist nur die Rückgabe eines klaren Ja/Nein mit Begründung:
    Java

    public record JudgmentResult(
        boolean success,
        String reason // "Das Ziel wurde verfehlt, weil der Aspekt X ignoriert wurde."
    ) {}

C. Der Hybrid-Ansatz (Empfohlen)

    Erster Check (Code): Schnelle programmatische Filter (Schema da? Pflichtfelder gefüllt? Werte im erlaubten Bereich?). Wenn das fehlschlägt, sofort abbringen (spart Token).

    Zweiter Check (LLM Judge): Wenn der Code-Check durch ist, bewertet der LLM-Judge die inhaltliche Qualität anhand des NodeGoal.

3. Wie fließt das Ergebnis der fachlichen Validierung in den Loop zurück?

Wenn die fachliche Validierung fehlschlägt, ist das kein harter Systemabsturz, sondern ein fachlicher Fehler, der genau wie ein Syntaxfehler in den Baum geschrieben und an den Planer übergeben wird:

    Der Schritt-Status im Baum wechselt von PENDING zu FAILED_SEMANTICALLY.

    Das JudgmentResult (inkl. reason) wird als errorFeedback direkt an diesen Knoten im Baum gehängt.

    Der Planer (dein Self-Healing-Loop) sieht nun im Baum: „Ah, Schritt 3 ist fehlgeschlagen, weil Grund X genannt wurde.“

    Das LLM entscheidet basierend darauf eigenständig: Entweder ein RETRY mit korrigiertem Prompt oder ein REPLAN (einen anderen Lösungsansatz wählen).

Damit stehen dir bei einer fachlichen Abweichung sofort drei gezielte Eskalationsstufen zur Verfügung, die du je nach Kritikalität des Schritts konfigurieren kannst:
1. Der gezielte Retry (Prompt-Refinement)

2. Die KI-gestützte Umplanung (Re-Plan)

    Wann: Auch nach 2 Retries wird das Ziel nicht erreicht, weil z. B. eine Datenquelle leer ist oder ein Tool nicht die erwarteten Infos liefert.

    Ablauf: Der Workflow-Planer übernimmt, erkennt die Sackgasse anhand des Knotenzustands und baut den Workflow-Baum dynamisch um (z. B. fügt er einen zusätzlichen Recherche-Schritt davor ein).

3. Human-in-the-Loop (Rückfrage / Eskalation)

    Wann: Es handelt sich um einen geschäftskritischen Schritt (z. B. „Vertrag versenden“ oder „Budget freigeben“), oder die KI meldet Unsicherheit (LOW_CONFIDENCE).

    Ablauf: Da dein Zustand bereits in der Datenbank persistiert wird, pausiert die Engine den Knoten einfach mit dem Status WAITING_FOR_HUMAN. Der Nutzer bekommt eine konkrete Rückfrage angezeigt. Sobald die Antwort vorliegt, wird sie in den Baum geschrieben und der Workflow läuft nahtlos weiter.

Der große Vorteil deines Designs

Für den Workflow-Designer (dich) bedeutet das: Du musst nicht mehr für jeden denkbaren Fehlerfall komplexe if-else-Verzweigungen manuell modellieren. Du definierst nur den Happy Path und die Zielkriterien (Acceptance Criteria) pro Schritt – den gesamten Fehler- und Ausnahmebehandlungs-Pfad übernimmt deine isomorphe Architektur zur Laufzeit selbst.

In einem isomorphen Workflow-System mit persistenten Chat-Sessions lässt sich dieses Problem jedoch extrem elegant und präzise lösen, ohne den gesamten Workflow blind von vorne starten zu müssen.

Hier ist der architektonische Ablauf, wie Agenten in so einem Szenario zusammenarbeiten und den Fehler korrigieren:
Der 4-Schritte-Ablauf zur Behebung von Upstream-Fehlern
1. Root-Cause-Discovery (Erkennung im aktuellen Schritt)

Agent in Schritt 4 merkt: „Ich kann meine Aufgabe nicht lösen, weil Parameter X fehlt.“
Er analysiert den Baum (der seinen eigenen Kontext bildet) und stellt fest: Dieses Datum hätte laut Definition in Schritt 1 erzeugt werden müssen.
2. Gezielte Cross-Session-Abfrage (Der Vorwurf / Die Nachfrage)

Anstatt den Workflow sofort abbrechen zu lassen, öffnet Agent 4 einen direkten Chat-Kanal zur Chat-Session von Schritt 1:

    Agent 4 an Agent 1: „In Schritt 4 fehlt das Feld customer_risk_score. Das hättest du in Schritt 1 basierend auf den Rohdaten ermitteln müssen. Warum fehlt es?“

3. Der "Memory-Patch" in der Chat-Session von Schritt 1

Weil Agent 1 seine eigene persistente ChatSession hat, muss er nicht bei Null anfangen. Er liest die Nachricht von Agent 4, greift auf seine eigene Historie zurück und erkennt seinen Fehler.

    Agent 1 antwortet: „Du hast Recht, ich habe die Rohdaten zwar gesehen, aber das Feld im JSON vergessen nachzureichen. Ich hole das nach.“

    Agent 1 aktualisiert seinen Output im Baum und speichert diese Erkenntnis in seiner Chat-Historie (damit er den Fehler nicht vergisst).

4. Selektives Rollback und Replay (Die Bereinigung der Zwischenschritte)

Da Schritt 2 und Schritt 3 nun auf veralteten/falschen Daten basieren, greift die Engine ein:

    Invalidierung: Die Status von Schritt 2 und Schritt 3 werden im Baum von SUCCESS auf DIRTY oder PENDING_REPLAY gesetzt. Ihre bisherigen Ergebnisse werden als "veraltet" markiert.

    Gezielter Re-Run: Die Engine führt Schritt 2 und Schritt 3 erneut aus – diesmal mit den korrigierten Daten aus Schritt 1.

    Fortsetzung: Sobald Schritt 3 durchgelaufen ist, bekommt Schritt 4 endlich die sauberen Daten und kann fehlerfrei arbeiten.

Warum dieser Ansatz genial ist

    Kein Totalverlust: Dank der Chat-Sessions wissen die Agenten in Schritt 1, 2 und 3 beim zweiten Anlauf genau, was schiefgelaufen ist. Sie korrigieren nur ihren Fehler, anstatt den kompletten Prozess zufällig neu zu raten.

    Vollständige Auditierbarkeit: Im Workflow-Baum und den Chat-Protokollen bleibt exakt dokumentiert: Schritt 4 hat gemerkt, dass Schritt 1 geschlampt hat -> Schritt 1 hat korrigiert -> Schritte 2 & 3 wurden neu berechnet. Für Debugging-Zwecke ist das ein absoluter Traum.

Wenn Schritt 2 bereits eine echte Transaktion ausgeführt hat (z. B. „Geld von Konto abgebucht“ oder „Bestellung im ERP angelegt“), kannst du ihn bei einer Upstream-Änderung nicht einfach wortlos überschreiben.

3. Wie behält das System hier den Überblick? (Lineage & Hash-Vergleich)

Da deterministische Services keine Intelligenz haben, die "nachdenken" kann, muss die Engine das für sie tun. Das gelingt über Input-Hashing:

    Jeder ServiceNode speichert einen Hash seiner Eingabedaten (inputHash) zusammen mit dem Ergebnis.

    Wenn sich ein Upstream-Schritt ändert, berechnet die Engine den Hash der neuen Eingaben für Schritt 2 neu.

    Ergebnis identisch? →
    → Schritt 2 muss nicht angerührt werden (Short-Circuit / überspringen).

    Ergebnis anders? →
    → Engine prüft: Ist der Service idempotent? Wenn ja →
    → Rerun. Wenn nein →
    → Saga-Kompensation einleiten.

1. Das Token-Bläh-Problem (Context Bloat & Attention Drift)

Du sagst: Workflow-Struktur und LLM-Kontext sind isomorph (identisch).

    Die unbequeme Frage: Was passiert, wenn dein Workflow auf 40 oder 50 Nodes anwächst und jeder Subagent eine lange Chat-Historie hat?

    Das Risiko: Wenn du diesen gigantischen JSON-Baum bei jedem Schritt als "Kontext" an das LLM übergibst, explodieren deine Token-Kosten und die Latenz. 2. Wer ist die absolute "Single Source of Truth"? (State-Chaos)

Du hast eine hochkomplexe Zustandstrennung: React Flow (Frontend-State), Java-Engine (Backend-State), Datenbank (Persistenz) und isolierte Chat-Sessions pro Agent/Subagent mit Sandbox vs. Commit.

    Die unbequeme Frage: Wie verhinderst du Race Conditions, wenn ein User in der React-Flow-UI manuell einen Knoten verschiebt oder ändert, während im Hintergrund ein Subagent asynchron chattet und die Java-Engine gerade einen Re-Plan in die DB schreibt?

    Das Risiko: Du baust dir unbemerkt ein verteiltes System mit inkonsistenten Zuständen. Der User sieht in React Flow etwas anderes als das LLM im Prompt, und die Datenbank weicht von beiden ab.

3. Das Reproduzierbarkeits-Desaster (Debugging Nightmare)

In der klassischen Softwareentwicklung gilt: Gleicher Input + gleicher Code = gleiches Ergebnis. In deinem System haben wir deterministische Services, stochastische LLMs, dynamische Re-Plans und Chat-Sessions.

    Die unbequeme Frage: Wenn ein Workflow in Production am Dienstag um 14:12 Uhr crasht oder ein komplett falsches Ergebnis liefert – wie um alles in der Welt reproduzierst du diesen Bug?

    Das Risiko: Da das LLM den Baum dynamisch umschreibt und Subagenten konversationell agieren, ist jeder Lauf potenziell einzigartig. Wenn du nicht jeden einzelnen LLM-Prompt, Token-Output und Chat-Turn unzerstörbar versionierst (Event Sourcing in Reinkultur), ist ein Post-Mortem-Debugging ein reines Ratespiel.

4. Prompt Injection im Workflow-Baum (Sicherheitsrisiko)

Die Pragmatische Validierungs-Matrix: Code vs. LLM-Judge

Es gibt eine goldene Regel in Agenten-Architekturen: Setze niemals KI ein, wenn Code das Problem deterministisch, schneller und kostenlos lösen kann.

Hier ist eine klare Entscheidungsmatrix für deine Workflow-Schritte, um Kosten, Latenz und Frustration gering zu halten:
1. Wo du KEINE LLM-Validierung brauchst (Nutzung von reinem Code / Schema):

    Strukturelle Integrität: Ist das JSON da? Sind Pflichtfelder belegt? →
    → Lösung: Jackson / JSON Schema / Bean Validation. (Läuft in Millisekunden, kostet 0 Cent).

    Datentypen & Formate: Ist es eine gültige E-Mail, eine IBAN, ein Datum im ISO-Format oder eine Zahl im Bereich 0 bis 100? →
    → Lösung: Regex oder einfache if-else-Prüfungen in Java.

    Exakte Daten-Matches: Stimmt die berechnete Summe im Service-Node mit dem ERP-System überein? →
    → Lösung: Mathematischer Assert im Code.

2. Wo LLM-Validierung (LLM-as-a-Judge) ZWINGEND notwendig ist:

    Semantische Vollständigkeit (Inhaltliche Qualität): „Enthält diese Zusammenfassung alle 3 kritischen Risikopunkte aus dem 50-seitigen PDF-Bericht?“ (Das kann kein Regex der Welt prüfen).

    Tone of Voice / Compliance: „Verstößt dieser generierte Kundentext gegen unsere Firmen-Richtlinien oder enthält er aggressive Formulierungen?“

    Logische Konsistenz in unstrukturierten Daten: „Passt die Antwort des Agenten in Schritt 4 inhaltlich zu den geschäftlichen Anforderungen, die in Schritt 1 definiert wurden?“

Wie baut man das pragmatisch in den Workflow ein? (Das "Shift-Left"-Prinzip)

Um das System performant zu halten, schaltest du die Validierungen immer nach dem Trichter-Prinzip (Funnel) von günstig nach teuer:

[ Input / Output ] 
       │
       ▼
 1. Schema-Check (Jackson / JSON) ──(Fehler)──► Sofortiger Retry (0ms, 0$)
       │
       ▼ (Erfolgreich)
 2. Programmatische Regeln (Code) ──(Fehler)──► Sofortiger Retry (1ms, 0$)
       │
       ▼ (Erfolgreich)
 3. LLM-Judge / Semantischer Check ──(Fehler)──► Nur wenn qualitativ nötig! (~500ms, Cent-Bruchteile)

Durch diese Kaskade fängst du 80 % der Fehler (Tastfehler, falsche Formate, fehlende Pflichtfelder) bereits in Millisekunden mit reinem Java-Code ab, bevor du auch nur einen einzigen Cent für einen LLM-basierten Evaluator ausgibst.
